## Findings

**1. Custom `:value-fn` is never applied in the new htable path (semantic divergence from stock).**
`emit-seq-map!` sets `child` to the raw `(jolt-nth entry 1 jolt-nil)` — the unmodified value `v`. Stock `write-object` computes `out-value (if default-value? v (value-fn k v))` before anything else happens with that value. There is no `value-fn`/`default-value?` reference anywhere in the new code. For the existing `pmap?` branch this is presumably handled inside `pmap-fold-seq-order` (which must pre-apply `value-fn` before calling the shared `emit-map-entry!`), but `emit-seq-map!` calls `emit-map-entry!` with the raw value instead. Consequence: a caller-supplied `:value-fn` option is silently ignored for sorted/tagged-table maps — output diverges from `json/write-str` whenever `:value-fn` is non-default. **No test exercises `:value-fn` on a sorted map** — this is the gap that would have caught it.

**2. `emit-map-entry!`'s omit-sentinel check operates on the wrong (untransformed) value.**
Same root cause as (1): `(jolt=2 (vector-ref stock-slots 9) child)` compares the sentinel to the *raw* value rather than the value-fn result. Even if (1) is fixed by applying `value-fn` before calling `emit-map-entry!`, this is worth calling out as a second symptom of the same missing step, since the omit mechanism (used to skip keys whose value-fn result equals the sentinel) can never fire for htable maps as written.

**3. Custom `:key-fn` is skipped whenever the key is already a string (semantic divergence).**
Stock: `out-key (if (and default-key? (string? k)) k (key-fn k))`. When `default-key?` is false (a custom key-fn is supplied), `key-fn` is invoked on **every** key, string or not. Native: `(if (string? key) key (observe (lambda () (jolt-invoke1 (vector-ref stock-slots 10) key))))` — this takes the string key verbatim and never calls `stock-slots[10]` (key-fn) at all when the key is already a string, regardless of whether a non-default key-fn was supplied. A custom `:key-fn` that transforms string keys (e.g., case normalization) silently has no effect for sorted/htable maps with string keys. **No test supplies a non-default `:key-fn`** — again the exact gap that hides this.

**4. Loop-guard re-invokes `jolt-seq` on an already-produced seq, and correctness depends on an unverified dispatch property.**
The loop binds `xs` via one `jolt-seq` call, then the `unless` guard immediately calls `jolt-seq` on that same `xs` again. This is only safe if `jolt-seq` is a cheap passthrough on an already-realized plain seq and only invokes a tagged table's custom `:seq` hook when the operand is itself a live tagged table. Every new test's custom `:seq`/`:next` implementation returns a *plain* Clojure seq/cons/lazy-seq as its continuation — none return a further tagged table with its own `:ops :seq`. So the double-call-per-iteration pattern is never actually exercised against a chained custom-table scenario. **Missing test obligation:** a custom `:seq` whose yielded continuation is itself a tagged table with `:ops`, to confirm the loop doesn't re-invoke (or misorder) a user hook relative to the single `(seq x)`/`(next x)` stock performs per step.

**5. `htable?` is absent from `emit-map-entry!`'s no-flush whitelist (performance-only, but worth flagging given the stated speedup claim).**
The whitelist that skips `flush!` before emitting a child covers `pmap?` but not `htable?`. A sorted-map nested as a *value* inside any map (the `(sorted-map "nested" (sorted-map ...))` test case) forces an extra flush/sync round-trip on every nesting level. This doesn't look like a correctness bug (the `observe` wrapper inside `emit-seq-map!` re-establishes consistent state regardless), but it undercuts the "~29% p50" improvement for any workload with nested sorted structures, and should be confirmed as an intentional scope limit rather than an oversight.

**6. Exception-safety of `observe` has only one exercised failure site.**
`observe`'s `sync!` is skipped if `thunk` throws; recovery depends entirely on the (unchanged) outer restorable-row mechanism. The new branch adds several *additional* flush/sync-bracketed call sites per entry (seq, first, nth×2, key-fn, next) beyond what previously existed for this map type, but the only exception test throws from the child's `-write`. **Missing test obligations:** throw from the key-conversion step (custom key-fn on a non-string key) and throw from the custom `:seq`/`:next` function itself, each followed by a subsequent successful row, to confirm every new `observe` boundary — not just the child-write one — recovers cleanly.

**7. `(jolt-nth entry 0/1 jolt-nil)` assumes a vector-shaped 2-tuple.**
All tests feed vector pairs (`["a" child]`). Untested: a custom `:seq` yielding list-shaped pairs or `MapEntry`-like objects, which is a plausible shape for "custom tagged-table seq operations." Worth a test or an explicit contract note.

**Net assessment:** the flush/sync discipline and seq/next/entry ordering relative to stock look carefully modeled, but the branch silently drops `:value-fn` handling and partially drops `:key-fn` handling for the htable path — both real behavioral divergences from stock `write-object`, not just untested edge cases, and both happen to be invisible because no new test configures non-default `:key-fn`/`:value-fn`.
