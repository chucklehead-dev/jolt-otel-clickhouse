## Review: payload-local scalar-map cache prototype

**Core mechanism (sound):** `payload_scalar_string_map_cache.ss` keys a weak-eq hashtable by the *live* HAMT root (`pmap-root`) or sorted-map tree pointer, never a copy. Since these are immutable persistent nodes, `eq?` identity on the root is equivalent to content identity, so reuse across repeated calls on the *same* source map is sound in principle. Stamp mismatch (cnt/ops) correctly forces a miss before any stale data is returned, and `same-policy?` is rechecked before/after lookup and before/after store, matching the docstring's promise (`any_value.clj:361-426`).

**Mutable sorted-map fields — handled, not a bug.** `sorted_scalar_string_map.ss`/cache rely on `:tree`/`:ops`/`:cnt` being mutable host fields (confirmed by `host/ref-put!` in tests). I traced both failure modes by hand: an `:ops` swap changes object identity so `stamp-matches?` (cache) *and* the admission re-check in `try-sorted-scalar-string-map` both reject it (`payload_scalar_string_map_cache.ss:34-40`, `sorted_scalar_string_map.ss:57-59`); a `:cnt` corruption makes `admitted-tree?`'s walk-count mismatch fail admission independently. Defense-in-depth works as claimed — not vacuous once traced, though the tests alone don't prove this (I verified against source).

**Genuine soundness gap — missing nonvacuity test (Medium).** Every test exercises `(convert m)` called twice on the *same* local `m` — a trivially-correct case for any pure cache. None constructs two **distinct** Clojure map values that happen to share an underlying root/tree pointer via structural sharing (e.g. `(let [b (dissoc (assoc a "new" "v") "new")] ...)`), which is the actual soundness claim this design rests on (identity of the *structure*, not the top-level map object). This is the load-bearing case for "payload-local identity reuse" and is currently unproven by the suite. Recommend adding it before adoption.

**Woven advice without Var replacement — explicitly out of scope, correctly disclaimed.** All eight policy-root guards (`scalar-string-map-payload-bindings`, `any_value.clj:348-359`) and the exporter's `key-string`/`value-string` identity guards (`chdb.clj:88-96,123-142`) use `identical?`/`eq?` on Var contents. None can detect in-place mutation of a function object that keeps the same identity (bytecode/closure patching, AOP-style weaving). The docstrings explicitly disclaim this ("trusted, not sealed against deliberate mutation," "not a cross-thread redefinition lock") — so this is a documented non-goal, not an undisclosed bug. Flagging only because the question asked for it explicitly.

**Loader coupling (Low, pre-existing pattern, not new).** `any_value_native.clj` now has three sequential top-level `(def ... (source))`-style macros (`:63-90`). If the newest resource (`payload_scalar_string_map_cache.ss`) is missing from a build, the whole namespace fails to load at the macro-expansion step, silently taking down the two previously-shipped scalar-map converters too (both are caught by `catch Throwable` at their `any_value.clj` call sites, so failure degrades to "no native fast path" rather than crashing — but the blast radius is now three features, not one). This mirrors the existing two-resource coupling already present before this change, so it's not a regression introduced here, just worth confirming CI packages all three `.ss` files together.

**Int64 fixnum-range check omission in the new loader — not a bug.** Unlike `scalar_string_map.ss`/`sorted_scalar_string_map.ss`, `payload_scalar_string_map_cache.ss`'s fencing macro skips the `most-negative/positive-fixnum` ⊆ Int64 check and the `jolt-fixnum->string` arity fence. Correct: this module never converts integers itself — it only caches already-converted results from the other two converters, which already enforce that bound.

**Exporter consumer (sound, single caller site).** `*sdk-scalar-map-payload-converter*` is bound once per `json-each-row-payload` batch and the encoder is forced to `:parallelism 1` at that call site (`chdb.clj:570-586`), matching the cache's documented single-thread contract. The simulated-factory tests (`chdb_sdk_payload_scalar_cache_test.clj`) correctly prove one-factory-per-payload and correct unwind-on-exception, but — as flagged by the prompt — don't exercise the real native cache end-to-end; that's deferred to the separate integration run already in progress.

**Adoption blocker:** none found in the traced logic itself; the missing structural-sharing nonvacuity test is the one gap I'd want closed before trusting the soundness claim beyond "same object called twice."
