## Review: `ffc-vector-fold` leaf-block loop (incubator/codec/src/jolt/traversal/kernel.ss:53–66)

### Blocking findings
None.

### Correctness
- The replacement loop resolves `pv-leaf-for` once per leaf and visits `chunk[offset..offset+run)`, where `run = min(len(chunk)-offset, n-i)`. This never reads past the chunk or past the logical count, and correctly truncates the final partial leaf.
- Visit order is preserved: the outer loop advances `i` by `run`, and the inner leaf loop visits offsets in ascending order — matching the original strictly-ascending per-index walk.
- Exceptions: no try/catch wraps the leaf loop, so a `visit` throw propagates immediately after already-called visits, with no partial/duplicate visits. This is confirmed by `experimental_test.clj`'s `exceptions-stop-before-later-callbacks-or-records` (seen = `(vec (range 33))` after throwing at x=32) and by `leaf_block_test.clj`'s call-count assertions.
- Reentry: the implementation uses only local `let`/named-`let` bindings, no shared mutable state, so nested/reentrant folds (`nested-folds-and-native-composition-are-isolated`) are safe — a `visit` that recursively drives another fold can't corrupt the outer loop's state.
- `n = 0` short-circuits before calling `pv-leaf-for`, matching `leaf_block_test.clj`'s "0 resolutions for empty vector" expectation.
- Fragility worth naming (not a regression, contingent on the stated trust in `pv-leaf-for`): if the resolver ever returned an offset equal to the chunk length for a valid `i`, `run` would be 0 and the outer loop would re-enter at the same `i` forever — a silent hang rather than an error. This sits entirely inside the declared trust boundary on the runtime primitive, so it's not a defect under that assumption, just a place where a future resolver contract violation fails worse (hang vs. index error) than the old per-element code did.

### Baseline/candidate equivalence and honest interpretation
`screen.clj` builds the "indexed" baseline by splicing the exact prior `ffc-vector-fold` body back into the *current* file text (not a separately maintained copy), isolating the comparison to this one function while both arms share identical JSON/codec code and SDK normalization caching. Output equivalence is checked via SHA-256 of full encoded bytes, with a changed-event negative control applied to both arms to prove the harness would catch a wrong-output regression, not just measure blind timings. ABBA ordering is used for both the micro and rich screens.

The written interpretation is appropriately honest: the micro fold speeds up consistently (~5x at 1057/5000/32769 elements per the table in `research/.../README.md`), while the rich 5,000-row projection/nested-JSON/outer-encoding screen is flat-to-slightly-worse on p50 and allocation (133.27ms→136.84ms, ~11,356B→11,357B/row) with only p99 improving. Both the CHANGELOG and research README state plainly that no overall rich-encoding throughput or allocation win is established, and explicitly warn against rerunning for a favorable median or quoting the micro result in isolation. No overclaiming found.
