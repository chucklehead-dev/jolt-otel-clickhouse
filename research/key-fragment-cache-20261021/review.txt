## Review: `research/key-fragment-cache-20261021` — do-not-adopt key-fragment cache prototype

**Blockers:** None structural. `check.clj` exercises the real failure surface: 15 scalar cases (Unicode, numeric edges, ordered/sorted/wide-128 maps, equal-but-distinct `String` keys with changed values), six limit/chunk-boundary cases plus one-under-limit throws, a completed-output-is-immutable check, and nested-scope close/retained-producer-rejects semantics. A hit-only throwing mutant proves the cache-hit branch (`key-fragment!`) is actually reached on a repeat key and not on a first occurrence — a real behavioral witness, not just a code-coverage proxy. A separate instrumented variant proves the 64-key admission cap holds (128-key map admits exactly 64) and that an off-by-one patch (`64`→`65`) is caught by the oracle. Importantly, these mutants are compiled from *separately instrumented copies*, not the exact timed candidate, so budget enforcement is verified for the patch text via the same exact-match transform, not observed live in the benchmarked build — a documented, low-risk gap rather than an unverified claim.

**Ownership/aliasing:** `key-fragment!`/`key!` in `key-writer.ss` copies out of the shared `tail` scratch buffer into a freshly allocated bytevector before storing it keyed by string content — it doesn't alias the mutable output buffer or the original key string, matching the comment's claim. One asymmetry worth flagging: the existing value-level cache (`json.ss` `map-cache`) uses a `weak-eq-hashtable` keyed by `pmap-root` identity (GC-reclaimable), while the new key cache uses a plain strong `string-hash`/`string=?` table keyed by content. That's fine given the hard 64-key/64KiB bounds and scope-finish clearing, but it's a different memory-ownership idiom than the pattern it sits beside, and it's new state a reviewer must track separately if this were ever revisited.

**Budget/order:** Caps (64 keys, ≤64 scalar chars, ≤1024B/fragment, ≤64KiB total) mirror the existing value-cache's shape (64/4096B/128KiB) at smaller scale; a key crossing a chunk boundary silently declines capture rather than erroring, consistent with the existing map-fragment pattern. Capture happens only after a successful full write (`eq? start-tail tail`), so a miss never does double work.

**Benchmark limits:** 16 observations/arm, A/B/B/A order, full-byte-equality control, and both changed-event and changed-attribute controls that perturb output in *both* arms — good non-triviality checks. But p95/p99 both equal the n=16 maximum (no tail claim), GC noise is visible and uncontrolled (gc_nanos ranges ~0 to ~168ms, ordinal 28 original spikes to 398ms), and only interpreted/source-mode was run — no native/release build, no repeated sweep.

**Verdict:** Keep unadopted. The control methodology (exact-match source patch, shared facade/SDK policy, byte-identical and changed-input oracles, budget mutants) is solid enough to trust the negative result itself, and the measured outcome is a net regression (~3.2% slower median, ~1.2% more allocation) within a noisy single-run screen — no case for revisiting without native-mode and larger-n evidence, and the real floor cost is elsewhere per the README's own attribution.
