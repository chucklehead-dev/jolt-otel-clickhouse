## Review: rich-sdk-scaling 1/2/4-lane evidence set (20261019)

**1. Fairness confound — queue slack hits zero exactly at lanes=4.** `rich-sdk-scaling-screen-20261019.clj:37-38` fixes *total* queue capacity at `4*n` (20000) regardless of lane count, then asserts `n <= queue-capacity`. Per-lane capacity is 20000/10000/5000 for 1/2/4 lanes — at lanes=4, capacity equals batch size exactly (zero slack), so the producer throttle (`>= queue-size queue-capacity`, lines 141-145) trips far more often than at lanes=1 (4x slack) or lanes=2 (2x slack). CPU-tick/throughput differences across the six arms are therefore confounded by lane count *and* available buffering at the same time — a delta between the lanes=4 and lanes=1 arms can't be attributed to lane count alone.

**2. Native concurrency — only intra-lane serialization is checked.** All lanes share one `conn` (`screen:68-74`, unchanged from the 18-era design). The only ordering invariant verified is `:serial-per-exporter` (`screen:173-176`), i.e. calls *within* a lane don't overlap each other. Nothing checks that calls from *different* lanes onto the shared Durable connection/native handle don't overlap. Going 2→4 lanes doubles the threads that can concurrently call the shared connection with no instrumented cross-lane guard; `stream-calls` just counts invocations, it can't detect overlap. Pre-existing limit, but lanes=4 is exactly where it matters most and the evidence doesn't demonstrate it was checked.

**3. Validator's full-batch invariant stays single-lane-only, at the tightest-margin arm.** `validate-rich-sdk-scaling-20261019.clj:33-35` only asserts exact 5000-row batches when `lanes=1` — unchanged from the prior `validate-rich-sdk-lanes-20261019.clj:27-29`, so not a new weakening. But lanes=4 (zero queue slack per #1) is the arm most likely to fragment batches, and it only gets the generic `1 <= rows <= 5000` check. A regression causing systematically undersized batches at lanes=4 would pass.
