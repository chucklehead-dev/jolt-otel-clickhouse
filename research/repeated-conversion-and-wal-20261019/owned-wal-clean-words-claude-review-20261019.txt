**1. (Confirmed by inspection, not execution) Stale SMT source-pin — `formal/smt/owned-wal-bounds/source-sha256.txt:1`.**
The digest recorded for `owned_ascii_wal.ss` is byte-identical in both worktrees (`2bbe2de2...`), yet the two `.ss` files differ by 12 lines (the new `word-has?`/`clean-word?` logic and fast-path branch). Two different file contents cannot both legitimately hash to the same sha256, so this branch's pinned digest was not regenerated after the edit. `scripts/check-owned-wal-bounds.sh:6` runs `sha256sum --check` against this file first — it will fail on this branch's current source. Beyond the stale hash, the SMT README (`formal/smt/owned-wal-bounds/README.md:17-25`) describes the modeled facts only in terms of the old single-byte-at-a-time emission ("advances input by 1 and output by 1, 2 or 6 bytes") — it never mentions the 4-byte aligned read/copy. So this isn't just a hash refresh — the model's fact-mapping needs to be extended to cover the new branch (or explicitly scoped out) before the "proof receipt" can be said to apply to this file. This is the one item I'd block on; everything else is advisory.
