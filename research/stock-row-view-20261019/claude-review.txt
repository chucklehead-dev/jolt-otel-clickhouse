## Review: stock row-view prototype (incubator/codec)

**Blocking findings: none.** I read the row-construction path end-to-end (Scheme record definition and emit logic in `json.ss`, the Clojure wrapper in `experimental.clj`, both test files, the CI workflow, README/CHANGELOG, and the research artifacts) and didn't find a correctness, ownership, aliasing, or limit-enforcement defect.

Specifics I verified:
- **Ownership/aliasing**: `ffc-json-row-box` stores the freshly-allocated native vector from the generated per-schema constructor as-is; that vector is never exposed back through any public accessor (`row-builder`, `append-row-fields`, `row-width`, `write-nested` all stay opaque). `ffc-json-row-append` shares the base vector between parent and child rows without copying, which is safe only because nothing in the API ever mutates it post-construction — consistent with the documented immutability contract, not a bug.
- **Reentry guard**: `append-row-fields` only accepts a row whose *current* suffix count is `0` (`row_view_test.clj:18` confirms a combined row rejects a second append), preventing unbounded append chains as documented.
- **Depth/size limits**: the row branch of `emit!` in `json.ss` increments `container-depth` identically to the existing map/vector branches, and the `depth [0 1 127 128 129]` test confirms rows hit the same max-depth=128 boundary as plain vectors, with identical pass/fail behavior at 128 vs. 129.
- **Value conversion order / unknown values**: fields are realized eagerly at construction (no lazy/convert-at-emit-time divergence), and unsupported values (`(Object.)`) are correctly rejected at `write-nested` time via the shared `emit!` dispatch, not silently dropped.
- **Row widths**: the `0..32` bound is enforced via `(integer? width) (<= 0 width 32)`, matching the 0/32 boundary tests and the documented 60+ arity-mask workaround; a 128-wide suffix appended to a 0-width row works as claimed.
- **Benchmark fidelity** (`screen.clj`): the harness slurps the live `otel/exporter/chdb.clj` source, replaces exactly one matching 24-field vector literal via `postwalk` with an `assert (= 1 @replaced)` guard, records a source SHA-256 for provenance, and requires byte-identical SHA-256 output between the vector and row arms (plus negative controls that mutate an event name and show the digest actually changes). ABBA ordering (32 observations/arm) and symmetric per-row assertions in both arms are sound. The reported result — ~6% estimated allocation reduction, no median-time win, and a *worse* sampled p99 — is accurately and explicitly caveated in both README and CHANGELOG ("no median-time or tail improvement," "p99 is the maximum of 32 observations, not a population-tail qualification"). Nothing here oversells the result, and no exporter/production file is touched. **Keeping this as a research checkpoint rather than promoting it to the exporter path is the right call** given a regressed p99 and no throughput gain.

**Actionable test gaps (non-blocking):**

1. **32-width rationale isn't traceable from source.** `row-builder`'s `(<= 0 width 32)` check in `experimental.clj` has no comment referencing the stock-runtime 60+ argument arity-mask defect that motivated the bound — that reasoning currently lives only in `research/stock-row-view-20261019/README.md`. If a future change (or a stock-Jolt upgrade) revisits this bound, there's nothing at the call site warning that it isn't an arbitrary API choice. Worth a one-line comment pointing at the native defect.
2. **Suffix-side value rejection is untested.** `row_view_test.clj` exercises unsupported-value rejection only for base fields (`(build 1 2 (Object.))`). There's no equivalent case appending an unsupported value via the suffix (e.g., `(append-row-fields c row [(Object.)])` then `write-nested`), nor a case passing a suffix containing itself-unsupported nested structure. Both paths funnel through the same `emit!`, so this is likely fine, but it's an asymmetry in coverage worth closing given how central the base/suffix split is to this feature.

No credential, env, or unrelated files were touched; CI test-count assertions (18/23/5 across the workflow, smoke test, and traversal-only gate) are internally consistent and arithmetically reconcile.
