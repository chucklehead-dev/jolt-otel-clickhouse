## Targeted review: research/fork-free-codec-20261019/

Scope: `traversal.ss`, `json.ss`, `probe.clj`, `oracle.clj`, `check-oracle.bb`, `benchmark.clj`, `run.sh`, `README.md`. Read-only inspection, no commands run. Ranked most actionable first.

**1. (High — unverified crash path) Bare-`hcoll` root not handled in `ffc-map-fold`.** `traversal.ss:7-13` dispatches on `(pmap-root m)`: if not `hnode?`, it assumes a flat alternating key/value vector and calls `(vector-length root)` directly. There's no branch for the root itself being a bare `hcoll` record. A map whose entire content is one fully-colliding pair (e.g. just `{"Aa" 1 "BB" 2}`, nothing else) plausibly needs no `hnode` wrapper and could store as a root-level `hcoll`. If so, `vector-length` on a record is a hard crash, not a graceful error. This shape is untested — the only genuine collision case (probe.clj:27, `{"Aa" 1 "BB" 2 "AaAa" 3 "BBBB" 4}`) mixes two hash groups, so its root is an `hnode` with `hcoll` children, not a bare `hcoll` root. Add an explicit root-`hcoll?` branch (or a clear assertion) plus a probe case for a lone two-key colliding map.

**2. (Medium — vacuous coverage) Lone-surrogate rejection never exercised.** `json.ss:44-45` rejects code points `0xD800..0xDFFF`. Nothing in `probe.clj`/`oracle.clj`/`benchmark.clj` encodes a string containing one. The README asserts this as settled Unicode handling, but the branch has zero coverage in this spike.

**3. (Minor — misleading precision) p95/p99 computed from 12 samples per arm.** `benchmark.clj:70-86` runs 12 samples per arm; at n=12, `ceil(0.95*12)=ceil(0.99*12)=12`, so both "p95" and "p99" are literally the sample max. The README caveats these as "not qualified production tails" but doesn't note p95/p99 are degenerate at this n — the labels overstate precision. Drop those labels at this sample size, or widen the run.

**4. (Informational, tested) `hcoll` order reversal undocumented.** `traversal.ss:22-26`'s collision branch recurses to the alist's end before visiting, reversing physical order — the opposite style from the file's other ascending-index loops, with no comment explaining why. It appears correct and is exercised (the Aa/BB/AaAa/BBBB probe case compares fold order against `(mapv vec m)`), but a future edit could regress it undetected outside that one fixture size. Worth a one-line comment tying it to `hcoll-alist`'s insertion-order convention.

**5. (Informational, not a defect) Asymmetric numeric fast-path range.** `json.ss`'s `integer!`/`emit!` spans INT64_MIN through UINT64_MAX — an unusual combined range, but deliberately boundary-tested in probe.clj:12-13 at all four edges, with correct single-fired signs (no double-sign, no missing sign) including both out-of-range bignum-fallback cases. Flagging only so this isn't mistaken for a bug — it's a documented, tested design choice.

**6. (Low) `ascii!` trusts external ASCII-only output unchecked.** `json.ss:22-24` writes `char->integer` directly as a byte, no range check. Safe for hardcoded literals, but also used for `jolt-flonum->string`'s output (json.ss:86), a stock/external formatter — nothing asserts its result is pure ASCII. Low severity, but an unvalidated dependency on a stock function's contract.

**Not flagged as defects:** byte-limit accounting, depth-limit off-by-one, bignum digit-buffer sizing (21 bytes correctly covers 20-digit UINT64_MAX), chunk reassembly, and per-call state isolation (no cross-call aliasing — confirmed by probe.clj:56-59) all check out by hand-trace. The benchmark's interleaved ordinary/direct ordering, outside-timed-interval equality check, and changed-input sanity check are sound for what they claim, and the README's scope disclaimers (no Durable/SDK/exporter measurement, no speedup claim over the selected encoder) accurately describe what `benchmark.clj` measures.
