## Review: Explicit codec integration (chdb.clj + incubator/codec)

Scope checked: the patch's full diff plus the referenced regions in `chdb.clj` (`load-experimental-span-codec!`, `execute-closed-compact-rows!`, `insert-direct-span-batch!`, `insert-direct-typed-span-batch!`, the `exporter` constructor validation/`let` nesting), `deps.edn`, and all three `incubator/codec` source files plus both test files.

### Findings (ranked)

**1. `load-experimental-span-codec!` discards the real failure cause (moderate, diagnostics correctness)**
`chdb.clj:1250-1261` wraps `require` + var resolution + `(open)` in a blanket `(catch Throwable _ ...)` and always rethrows the same generic message, "Experimental span codec requires its explicit source alias," with no `:cause`/ex-data passthrough. But `jolt.codec.experimental`'s `backend` delay (`experimental.clj:12-28`) can itself throw a distinct, legitimate signal — `ex-info "Unsupported experimental codec runtime" {:type ::unavailable}` — when the structural self-check (`qualify`/`scalar` probes) fails, i.e. the alias *is* on the classpath but the running Chez/Jolt build doesn't match the `runtime7098`/`stock 0.8.23` assumptions the codec is qualified against. Today an operator who has correctly added the alias but is running an unqualified runtime gets told to add "its explicit source alias," which is already present — actively misleading for the one failure mode this module is most exposed to (the two-runtime qualification fence is the whole point of the incubator scoping). This is a real defect in observability, not a missing-feature gap: fail-closed behavior is preserved (exporter construction still throws before DB acquisition), but the diagnosis is wrong.

**2. `deps.edn` alias is not actually "source-only" despite the docstring's claim (minor, packaging hygiene)**
`chdb.clj:1794-1795` documents: "True requires the source-only `:experimental-span-codec` alias." The alias itself (`deps.edn:22-23`) is `{:extra-paths ["incubator/codec/src" "incubator/codec/test"]}` — it puts the codec's **test** namespace on the classpath alongside its source whenever activated. That's not harmful by itself (tests aren't auto-run), but it contradicts the "source-only" framing in the docstring and means any consumer who activates this one alias for a production export path also gets `jolt.codec.experimental-test` and `otel.exporter.chdb-experimental-codec-test` resolvable on their classpath. A cleaner split (separate `:experimental-span-codec` / `:experimental-span-codec-test` aliases) would match the stated contract; as written it's a documentation/implementation mismatch rather than a functional bug.

### Confirmed correct (audited, no defect found)

- **Prefix-excluded payload budget**: `ffc-json-encode`'s `budget = limit + (string-length prefix)` (json.ss:15) correctly keeps the prefix outside the caller-supplied `max-bytes`, matching `encode-prefixed-records`'s docstring and `chdb.clj`'s call with `(insert-byte-limit)`. The `experimental_test.clj` boundary tests (`explicit-wire-values-and-prefix-budget`, `scalar-and-prefix-chunk-boundaries`) exercise the exact ensure-space!/resize boundary and the off-by-one reject case; the arithmetic holds under trace.
- **Synchronous, no-readahead record order**: `ffc-records-fold` (traversal.ss:63-68) walks non-vector sources via `seq`/`seq-more` one element at a time, and `emit!`'s lines-mode calls `project` inside the same per-row lambda before requesting the next element — matches `failure-stops-before-next-record`'s assertion that only the failing row (and nothing after it) is observed.
- **Lexical isolation**: the Scheme backend is built via one `scheme/eval-string` of `(let () ...)`, not installed at the Scheme top level; `reentry-and-independent-output` explicitly asserts `(rejects? #(scheme/proc "ffc-json-encode")))`.
- **Immutable owned snapshot / no-replay fallback**: `execute-closed-compact-rows!`'s codec branch (`chdb.clj:1286-1297`) calls `(:encode codec)` once to produce finished bytes, then does `(or (owned-statement/try-snapshot bytes) (String. bytes "UTF-8"))` — strictly post-hoc wrapping of already-encoded bytes, never re-invoking `project`/row producers.
- **Default-path preservation**: when `:experimental-span-codec` is `nil` (the default), `insert-direct-span-batch!`/`insert-direct-typed-span-batch!` fall through to byte-for-byte the pre-patch row construction (`(map #(span-row % nil true) spans)` / `(into (span-row span nil true) (projector span))`).
- **Before/after compact-plan and codec identity fences**: both `direct-span-layout?`/`direct-typed-span-layout?` checks and the new `(identical? codec (:experimental-span-codec snapshot))` guards run both pre- and post-encode (`initial-snapshot` then `snapshot`), exactly as asserted by `row-shape-and-post-encoding-plan-check-before-execute`'s `[:plan :plan :execute]` ordering. Since `:experimental-span-codec`/`:durable?`/`:json-backend`/`:insert-format` are never `swap!`'d post-construction (verified against every `swap! state` site in the file), this is currently unreachable defense-in-depth, consistent with the file's existing style for `:typed-span-projector`.
- **Initialization before storage**: the `let [experimental-span-codec (when experimental-span-codec? (load-experimental-span-codec!))]` now wraps the remainder of `exporter`, strictly before `jdbc/connection`/DDL; `invalid-opt-in-never-opens-storage` confirms zero connection attempts for invalid option values.
- **No WAL/persistence bypass**: `execute-durable-sql!` dispatches on `(string? sql)` vs. owned-statement, but both branches still require `(:status result)` in `confirmed-durable-statuses` — the codec cannot produce an unconfirmed/unchecked write.

The surrogate-pair handling in `escaped-char!` (json.ss:48-49) initially looked suspicious (unconditional "unpaired surrogate" error for any codepoint in `0xd800`-`0xdfff`) but is consistent with Chez/Jolt strings storing full Unicode scalar values per char rather than UTF-16 code units — `write-nested`'s test (`"é😀"` → `\ud83d\ude00`) confirms supplementary-plane characters arrive as single >0xFFFF codepoints and are deliberately re-split by `u16!`, not pre-split by the host string representation. This is a trusted-runtime-representation assumption, not a bug, and matches the stated `runtime7098`/Jolt-0.8.23 qualification scope.
