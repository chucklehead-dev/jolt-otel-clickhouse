## Review findings

**1. Byte-budget vs. char-length mismatch is a real (if conservative) semantic gap, not just an optimization limit.**
`default-string-value-max-chars` / the native `maximum` arg is `(quot max-bytes 4)` — a worst-case UTF‑8 bound. But `try-scalar-string` (the oracle) bounds strings by **byte count** (`string-bytes value <= max-bytes`), while the native kernel's `admitted?` bounds by **character count** (`string-length`). These are different metrics reconciled only by a 4×-safety margin. That margin holds for UTF‑8 (max 4 bytes/codepoint), but nothing in the kernel or loader verifies the host's `string-length` counts *codepoints* rather than UTF‑16 code units. If Chez's `string-length` ever counted surrogate pairs as 2 (it doesn't today, but this isn't asserted anywhere), the margin assumption would silently erode for astral-plane-heavy strings. Worth an explicit comment/assertion tying the `/4` divisor to "string-length counts codepoints," since that's load-bearing and undocumented.

**2. `try-scalar-string-map` has no Clojure-side identity guard, unlike its two siblings.**
`try-scalar-string`, `default-scalar-string?`, and `default-string-value-max-chars` all explicitly check `(identical? ...)` on the relevant vars before doing anything. `try-scalar-string-map` instead unconditionally forces/calls the native delay and relies entirely on the Scheme kernel's `same-policy?` to detect drift. This is consistent with the stated design ("private implementation roots... trusted") and is covered by the before/after `same-policy?` calls, but it means policy-drift detection for this one function lives in a different language/trust boundary than its siblings — a divergence worth a one-line comment explaining why (so a future reader doesn't "fix" it into redundancy or, worse, assume parity and skip re-verifying the native side when editing the Clojure anchors).

**3. Fixnum/Int64 bound check is dropped entirely in the native fast path.**
`admitted?` only tests `(fixnum? v)` — it never consults the `min-int64`/`max-int64` bindings it was handed. Correctness today rests entirely on the stated pinned-runtime guarantee (native fixnums ⊆ Int64). That's explicitly acknowledged as out of scope, but concretely: the `bindings` vector threads `min-int64`/`max-int64` through `same-policy?` purely to detect *redefinition* of those vars, not to bound-check values — so if someone redefines `max-int64` to something narrower than native fixnum range, `same-policy?` will correctly decline (good), but there's no defense if the *native fixnum width itself* changes (different Chez build) without the Clojure anchors changing. The loader's `source` macro does assert record-type layout and helper arities, but nothing asserts fixnum width vs. Int64 width at load time — that assumption is unchecked at any layer.

**4. `copy-node`'s metadata-drop behavior for `text` is correct but silent on NaN/-0.0-class edge cases.**
Not applicable here since floats are already excluded by `admitted?` (only `boolean?`/`fixnum?`/bounded `string?` pass) — no bug, just confirming the exclusion is complete: `admitted?`'s cdr check has no `else` branch returning true, so any value type not listed (including floats, nil, keywords) correctly falls through to decline. Good.

**5. Unsupported-host fallback (`catch Throwable _ (constantly nil)`) swallows load errors unconditionally**, including the loader's own assertion failures (unsupported layout/helpers) — correct per spec ("decline without dropping data"), but means a broken *compile* of the `.ss` resource is indistinguishable from "runtime unsupported" at the call site. No test exercises a genuinely malformed resource to confirm decline-not-throw holds for compile-time errors specifically (vs. the asserted runtime checks it does test).

No issues found with: identity-guard placement in `canonicalize`/`default-scalar-result`, the exporter's double-check-before/after pattern (`sdk-scalar-attrs`), or test coverage for order/metadata/kind preservation.
