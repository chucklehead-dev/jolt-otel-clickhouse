## Review: sorted collection vs. function equality (commit 388a3ad6)

**Dispatch order confirmed unchanged.** `jolt=2` (values.ss:568-638) answers scalars/pvec/pmap/pset/jrec directly, then falls to `jolt-eq-arms`, walked head-first; `register-eq-arm!` conses (values.ss:524-527), so the registry is LIFO — any arm registered *after* the core sorted arm (i.e. any user/library extension, since core loads first) is checked *before* it. `sorted-fast=` (host-table.ss:331-367) only runs once the sorted arm's own predicate `(or (htable-sorted? a) (htable-sorted? b))` (host-table.ss:368) has already won that walk. The new `(procedure? o) 'ne` branches (host-table.ss:347, 359) sit inside that arm, so they cannot preempt a user predicate — confirmed by the test at sorted-test.ss:97-109, which registers an extension keyed by `eq?` identity on the raw sorted value and shows it still intercepts.

**No legitimate map/set representation is also `procedure?`.** Map/set-as-callable in jolt is dispatched through a separate generic apply path keyed on `pmap?`/`pset?` (collections.ss:1296), not by making `pmap`/`pset` themselves Scheme closures. This matches `jolt=2`'s own pre-existing `(and (procedure? a) (procedure? b)) #f` fast path (values.ss:613), which already treats fn-vs-fn as identity-only. So the new rejection only fires on genuine ordinary functions, never on a disguised collection.

**Real, untested compatibility gap.** Before this change, a (sorted-coll, procedure) miss fell through `sorted-fast=`'s `(else #f)` to the shared fallback (host-table.ss:376), which normalizes the sorted side to a concrete `pmap`/`pset` and **re-dispatches** `jolt=2` on that pair — re-walking the *entire* `jolt-eq-arms` registry a second time, now with a plain collection operand. Any extension arm written to match `pmap?`/`pset?` concretely (rather than the raw sorted wrapper, or `map?`/`set?`/`coll?`, which already includes `htable-sorted?` per host-table.ss:308) would only ever have been reachable against a *sorted* operand via that second, post-normalization pass. The new `(procedure? o) 'ne` branch answers before that normalization ever happens, so such a "normalized-operand-only" extension stops being consulted for the (sorted, procedure) pairing specifically — while still firing for a plain-collection vs. procedure pairing. That's a narrow but genuine contract change, not just a performance win, and it is exactly the shape of risk the motivating "default-marker" library experiment describes (a marker procedure intentionally compared equal to a collection). The included regression test only exercises identity-on-the-raw-sorted-value extensions (sorted-test.ss:97-109); nothing exercises a `pmap?`/`pset?`-keyed extension against a sorted operand, so this is a real missing negative control, not a theoretical one.

**Callback-elision claim holds for the case actually changed.** The old normalize-then-redispatch path for a procedure opponent could run `sc-tree-fold`/`pmap-assoc`/`jolt=2` key callbacks before concluding false (as the PR motivation states); the new path runs none for that pairing. The sorted-vs-sorted and sorted-vs-plain branches that remain unchanged use the identical lockstep/fold logic as before — no new callback-ordering risk is introduced there, only removed for the one pairing (procedure) that can never be a legitimate match.

**Verdict:** the fast-reject logic itself is sound and well-targeted — it cannot misfire against a disguised collection, and it does not reorder the extension registry. The one open risk is real but narrow: it silently removes the implicit post-normalization re-dispatch chance for any equality extension that recognizes only the concrete plain-collection type (not the sorted wrapper or a general coll predicate) when the other operand is a bare procedure. Before calling this "the" fix, either add a negative-control test for a `pmap?`/`pset?`-keyed extension against a sorted operand + procedure, or confirm no such extension pattern exists/is supported.
