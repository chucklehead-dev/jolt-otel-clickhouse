**Finding 1 — No local containment if the new SDK scalar-map converters throw instead of declining.**
`try-sdk-scalar-attrs` (`chdb.clj:116-126`) calls the SDK's `try-scalar-string-map`/`try-sorted-scalar-string-map` with no `try/catch`. The whole design assumes these helpers always return `nil` for anything they can't convert (nested values, non-string-representable scalars, oversized maps, custom map types) rather than throwing. The in-patch tests only probe known edge cases (nil, float, nested, alias keys, oversized maps) and confirm `nil`-return behavior for those, but that's a contract assumption about an external dependency (`otel.any-value`), not something enforced at this call site. If a future otel SDK revision (or an input type not covered by the test fixtures, e.g. a custom record implementing a scalar-like interface) causes the helper to throw instead of decline, export now hard-fails instead of falling back to `small-attribute-transform`/the generic `into {}` path the way the old code always could. This mirrors the pre-existing lack of a catch around `small-attribute-transform`'s *invocation* (only its `require`/`ns-resolve` is guarded), so it's not a regression in kind, but this patch adds a second call path with the same unguarded exposure, now gating the literal whole attribute-conversion path on every native-backend export call. Worth a defensive `catch` or an explicit upstream contract test.

**Finding 2 — Inconsistent CI alias composition between twin test files.**
In `.github/workflows/tests.yml`, `sdk-scalar-map-test` runs standalone (`-M:sdk-scalar-map-test`) while the structurally parallel `sdk-sorted-scalar-map-test` runs combined with the native pin (`-M:native-json-byte-batch:sdk-sorted-scalar-map-test`). Neither test file actually exercises `clojure.data.json.jolt-native` (no `write-prefixed-batch-bytes!`/native JSON writer calls) — both only exercise `otel.exporter.chdb/attrs` via the `:native-guarded-byte-batch` backend flag, which is independent of the native-JSON dependency alias. This asymmetry looks like a copy/paste residue rather than a deliberate choice; left as-is, the sorted test coincidentally always runs against the native data.json pin while its scalar-map sibling never does, which can silently produce divergent coverage if either dependency's SHA moves again. Recommend either dropping `:native-json-byte-batch` from the `sdk-sorted-scalar-map-test` CI line or adding it to `sdk-scalar-map-test` for symmetry.

No other concrete defects found in the reviewed files; the dependency/SHA bookkeeping and oracle-mutant claims in the review packet check out against the actual diff.
