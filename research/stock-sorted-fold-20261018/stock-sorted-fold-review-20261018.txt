## Review: bounded native fold for stock sorted scalar maps

**Verdict on the core question:** under the stated trust boundary, the fold does not skip user-observable behavior for *admitted* maps. Per-entry handling is identical to the slow path (same `emit-map-entry!` closure is reused by both the fold and `emit-seq-map!`'s loop), value emission still goes through full protocol dispatch (`emit!` on each child), and the in-order left/visit/right traversal matches the stock ascending walk's node order. Critically, `host-table.ss`'s `sc-tree-seq` (the no-from-key, whole-tree case the fold mirrors) never calls the comparator — it only pushes left/right spines — so bypassing the comparator in the fold is not a divergence, it's faithful to what the stock seq already does for this exact case. The admission gate (identity-checked `:ops`, tag, bounded/fully-walked tree, string keys, scalar values, `cnt == seen`) also correctly declines the *entire* map on any single disqualifying node, so there is no partial-admission risk (nested collections as values, non-fixnum numerics, non-string keys all force full fallback to `emit-seq-map!`).

That said, three concrete issues should block calling this "credible" as-is:

**1. Empty-map correctness is accidental, not designed.** `task-stock-sorted-scalar-tree` signals success by returning `tree` itself (not a separate boolean). For an admitted *empty* sorted map, `count = 0` and `tree = jolt-nil`. The installer's injected branch is:

```scheme
(let ((tree (task-stock-sorted-scalar-tree x)))
  (if tree (begin (byte! 123) (task-stock-sorted-fold tree emit-map-entry! #f) (byte! 125))
      (emit-seq-map! x)))
```

This only produces the correct `{}` because `jolt-nil` happens to be a non-`#f`, hence truthy, Scheme value, so the fast branch is taken, and `task-stock-sorted-fold` on a `jolt-nil` tree is defined to short-circuit to `acc` (`#f`) via its own `(if (jolt-nil? tree) acc ...)` check — producing an empty object. If the host's `nil` representation or the admission function's return convention ever changes (e.g., to explicitly return `#f` for an empty tree, which would be the more defensive choice), this silently flips to calling `emit-seq-map!` instead — still correct, but the current code's correctness for `count=0` depends on an implicit nil/false distinction the probe comment never states as intentional. This needs either an explicit `(and tree (not (jolt-nil? tree)))`-shaped guard or a dedicated empty-sorted-map test; neither is present among the four files reviewed.

**2. No visible test exercising the admission boundary itself.** None of the four files is a test; the only runtime evidence offered is a benchmark over 2000 unspecified real spans plus `a18e06`'s existing byte-writer tests (not part of this probe's own validation). The admission predicate has several boundary conditions that are easy to get subtly wrong and aren't demonstrated as checked anywhere in these files:
   - exactly 128 vs. 129 nodes (the `(< seen 128)` / `(<= 0 count 128)` combination),
   - a value that is a ratio, bignum, or flonum (must decline — only `fixnum?` is accepted, not `integer?`),
   - a map whose `:cnt` field disagrees with the actual node count (must decline via `(= count seen)`),
   - a sorted map/set built with a custom comparator but the *same* stock `:ops` table (ordering must still come out ascending from pure left/right structure, which the code should handle correctly, but this is exactly the kind of case worth a positive test given the packet explicitly calls out comparator callbacks as part of the contract).

**3. The ops-identity capture strategy is unverified beyond a type smoke-test.** `task-stock-sorted-ops` is captured once, at probe load, as `(var-cell-root (jolt-var "clojure.core" "sm-ops"))`. The installer's only check on this is `(assert (scheme/eval-string "(pmap? task-stock-sorted-ops)"))` — that proves the captured value is *map-shaped*, not that it is the same object (`eq?`) a freshly constructed sorted map will store in its `:ops` field during this same process lifetime. If `var-cell-root` returns a dereferenced snapshot rather than a live, stable reference to whatever object `PersistentTreeMap` instances actually share, the admission check could silently and permanently fail closed (always falling back, which is safe but means the fast path never fires and the benchmark numbers wouldn't reflect this code path at all), or — more concerning — could succeed only for maps created before some var-root rebinding and fail after, producing inconsistent performance/semantics within a single run. This is the one place a wrong assumption wouldn't just degrade to the slow path safely in all cases; it needs a direct test that creates a real `(sorted-map ...)` in the *same* diagnostic process after `load-payload-byte-buffer-writer!`/probe install and confirms `task-stock-sorted-scalar-tree` admits it with a non-`#f`, non-`jolt-nil` tree for the nonempty case.

**Scope note:** I did not evaluate the byte-writer's unrelated mechanics (string caching, batch/row reentrancy, `render-empty-string`) since they're identical for sorted and non-sorted maps and the packet's question is specifically about the fold's semantic viability, not the writer's general correctness, which `a18ae06`'s existing tests already cover.
