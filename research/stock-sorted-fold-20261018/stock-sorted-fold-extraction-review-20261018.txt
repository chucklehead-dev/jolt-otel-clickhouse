## Clearly scoped qualification gap

The optional-helper detection in `jolt_byte_writer.ss:4-12` is pure arity-mask duck typing:

```
(bitwise-bit-set? (procedure-arity-mask admit) 1)
(bitwise-bit-set? (procedure-arity-mask fold) 3)
```

This proves nothing about *behavior* — only that something bound to those two names accepts 1 and 3 arguments respectively. The packet's own contract text ("Unsupported options preserve fallback... absent/unsupported arity keeps old sequence path") asserts a decline-on-wrong-arity guarantee, but the only test exercising this detection gate (`optional-helper-absence-keeps-same-bytes` in `json_stock_sorted_fold_test.clj:35-42`) shadows `top-level-bound?` to simulate *absence*, not *presence with incompatible arity*. No test in the reviewed set binds `stock-sorted-map?`/`sorted-map-fold-seq-order` to stubs of the wrong arity and checks that `djn-stock-sorted-map-folder` resolves to `#f` and falls back correctly. The arity-check branch of that `and` chain is therefore unexercised — this is a missing-qualification gap in the given evidence, not a source defect (the logic itself looks correct by inspection; it's just unverified by the supplied tests).

## Minor note, not a defect

`djn-stock-sorted-map-folder` is computed once at file-load time (line 4, top level), capturing the `admit`/`fold` procedure objects directly rather than re-resolving the vars per writer invocation. This matches the file's stated design ("helper closures are constructed once, not once for every row") and is consistent with how other per-factory state is handled, so it is not a new defect — but it does mean that if `stock-sorted-map?` or `sorted-map-fold-seq-order` were ever redefined *after* this module loads (hot-reload), the writer would keep using the stale procedures rather than re-checking. Nothing in the reviewed files suggests that scenario is supported or expected, so I flag it only as an implicit assumption, not a gap requiring action.
